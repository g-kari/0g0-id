# OWASP ASVS 5.0.0 ギャップ分析（目標 L2）

Issue #269。アプリケーションコードは変更していない。判定は 2026-11-12 時点の `master` のソース、テスト、リポジトリ内の文書に基づく。

## 判定の読み方

目標は ASVS の Level 2。L2 は L1 を含むので、CSV の `L` が `1` または `2` の 253 件を目標集合にした。`L` が `3` の 92 件も同じ基準で判定し、すでに満たしているもの、または小さな追加で届くものには本文で触れる。

| 判定    | 意味                                                                                          |
| ------- | --------------------------------------------------------------------------------------------- |
| met     | 要件を満たす実装または、このリポジトリが持つ設定がある。テストがある場合はパスを添えた。      |
| partial | 一部の経路や文書だけが要件に届いている。                                                      |
| not met | このアプリに要件が当てはまり、対応が無い、または実装が要件と矛盾する。                        |
| N/A     | パスワード、ファイルアップロード、GraphQL、WebSocket、WebRTC、SAML のように、対象機能が無い。 |

対象は `workers/id`、`workers/user`、`workers/admin`、`workers/mcp`、`packages/shared`。外部の Relying Party の実装、Cloudflare ダッシュボード、本番シークレットの値は見ていない。プラットフォームに依存する TLS や保管時暗号化は、リポジトリに設定または文書が無い限り充足にしていない。

`docs/proposals/` は未実装の提案として扱い、満たした根拠にしない。パスキー、メール登録、Discord、Steam はソースにあるが既定オフなので、有効化したときに効く要件にはその条件を書いた。

- URL: https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/docs_en/OWASP_Application_Security_Verification_Standard_5.0.0_en.csv

## 優先して埋めるギャップ

深刻度は、この IdP で悪用されたときの到達点で並べた。上から五つが今回の優先五件。提案は実装していない。

### 1. 管理画面の蓄積型 XSS（High）

該当: V1.2.1（not met）、V3.2.2（not met）。

`workers/admin/frontend/src/pages/users/index.astro` は利用者の `name` と `email` を `innerHTML` にエスケープせず入れる。表示名は OAuth プロバイダ経由で利用者側の値になる。管理者オリジンでスクリプトが動くと、セッション Cookie は HttpOnly でも同一オリジンの管理 API を呼べる。`workers/user/frontend/src/pages/profile.astro` の `getInitials` と `workers/user/frontend/src/pages/device.astro` の scope 文字列も同じ種類の抜けである。`escapeHtml` は `packages/shared/src/frontend/helpers.ts` にあり、連携一覧やセッション一覧では使われている。

提案: 動的な HTML を `textContent` か `escapeHtml` に揃える。管理ユーザー一覧を最初に直す。

### 2. 単一要素のまま管理者にも入れる（High）

該当: V6.3.3（not met）、V6.8.4（not met）、V10.3.4（not met）。

Google などの上流へのログイン一回で、利用者セッションも管理者セッションも作れる。アクセス トークンに認証強度を載せず、リソース側も見ない。パスキー経路は `PASSKEY_LOGIN_ENABLED` が真のときだけで、有効にしても第二要素ではなく別の単一要素になる。本番用のパスキーテーブルは `migrations/` に無く、`docs/proposals/` 側にある。

提案: 管理者はパスキー、または上流 ID トークンの `amr` に MFA が含まれることを必須にする。そのクレームを自前トークンへ引き写し、管理 API で拒否する。

### 3. リフレッシュに絶対寿命が無い（High）

該当: V7.3.2（not met）、V7.3.1（not met）、V10.4.8（not met）。

`workers/id/src/utils/token-pair.ts` の `issueTokenPair` は、ローテーションのたびに `expires_at` を現在から 30 日後にする。family の初回発行時刻では切らない。使い続ける限りリフレッシュが更新される。無操作で切るアイドル期限は別途無い。BFF Cookie の `BFF_SESSION_MAX_AGE_SECONDS` は 7 日だが、リフレッシュ成功で置き直される。`ARCHITECTURE.md` の Cookie 行は 30 日のままで、コードと食い違う。

提案: family の作成時刻を保持し、絶対期限の後はリフレッシュを拒否する。アイドル期限はそれより短くする。文書の日数をコードに合わせる。

### 4. 認可サーバーに同意が無い（High）

該当: V10.7.1（not met）、V10.7.2（not met）。撤回 UI の一部は V10.7.3（partial）。

第三者クライアントへの認可で、利用者にクライアントと scope を示して同意を取る画面が無い。影響を下げる制御として、RP の userinfo は `cid` があると `sub` だけを返す（`workers/id/src/routes/userinfo.ts`、`packages/shared/src/lib/privacy.ts`）。`docs/rp-profile-minimization-migration.md` も同意を未完了と書いている。連携の切断は `workers/user/frontend/src/pages/connections.astro` からできる。

提案: 第三者の `/auth/authorize` でクライアント名、要求 scope、リダイレクト先を表示して保存する。第一者 BFF は事前登録の例外にできる。利用者は付与を後から撤回できるようにする。

### 5. 上流 IdP のアサーションを検証していない（High）

該当: V6.8.2（not met）、V10.5.4（not met）。関連して V10.5.1 と V10.2.2 は partial。

自前の JWT は ES256 で `iss`、`aud`、`exp` を検証する（V9 は充足）。上流の Google 等は認可コードをトークンに交換したあと userinfo を信頼する。ID トークンの署名、issuer、audience、nonce は見ていない（`packages/shared/src/lib/google.ts`、`workers/id/src/utils/provider-resolution.ts`）。Discord コールバックだけクエリの `iss` を見ている。

提案: OIDC の上流では、ユーザー作成の前に ID トークンを固定 issuer、自クライアント ID、ログイン時に保存した nonce で検証する。

## 章ごとの要点

### V1 Encoding and Sanitization

インジェクションの大半は、このスタックに存在しない技術（OS コマンド、LDAP、XML、JNDI）なので対象外にした。SQL はプレースホルダで足りている。足りないのは HTML の出力エンコードで、管理ユーザー一覧に具体的な抜けがある。

### V2 Validation and Business Logic

サーバ側の検証と、BAN やロール変更のトランザクションはある。業務上限の文書と、ロックアウトの本番接続が弱い。在庫の二重予約のような要件は業務が無いので対象外。

### V3 Web Frontend Security

セッション Cookie の属性は `__Host-`、`HttpOnly`、`Secure`、`SameSite=Lax` で揃っている。セキュリティヘッダーは id / user / admin の Worker 応答に付く。MCP と、Worker を通らない静的ファイルには付かない。テキストの安全な描画は画面によって差がある。

### V4 API and Web Service

GraphQL と WebSocket は無い。HTTP のフレーム処理は Workers ランタイムに依存する。アプリが持つのは Content-Type、信頼するプロキシヘッダー、CORS の固定オリジン。

### V5 File Handling

ファイルの受付、展開、ダウンロード機能は無い。章ごと対象外。

### V6 Authentication

パスワードは無い。認証は上流 OAuth の単一要素で、MFA も認証強度の確認も無い。自前 JWT の検証は別章で足りているが、上流の ID トークンは検証していない。ロックアウトの関数は本番経路から呼ばれない。

### V7 Session Management

サーバ側でのセッション検証、ログアウト、BAN 時の一括失効はある。リフレッシュは使うたびに 30 日延び、絶対寿命とアイドルタイムアウトは無い。利用者画面のログアウトはプロフィールにしか無い。

### V8 Authorization

管理者、本人、サービストークンの分離はサーバ側にある。RP へのフィールドは `sub` に落ちる。認可規則を一枚にまとめた文書は無い。文脈（場所やデバイス）による認可は無い。

### V9 Self-contained Tokens

自前の JWT は ES256、固定の検証鍵、`iss` / `aud` / `exp` を検査する。トークン種別（typ）の拒否だけが弱い。

### V10 OAuth and OIDC

認可コード、PKCE（公開クライアントと `/auth/authorize`）、redirect の登録照合、一回限りのコード、60 秒のコード寿命はある。同意画面は無く、機密クライアントの PKCE は任意で、リフレッシュに絶対期限は無い。動的クライアント登録は無認証だが、公開クライアントとレート制限で緩和している。

### V11 Cryptography

実装は WebCrypto と jose に寄っている。AES-GCM、ES256、SHA-256、CSPRNG は確認できる。鍵とアルゴリズムの台帳が無い。パスワードハッシュは対象外。

### V12 Secure Communication

外部 URL は https。TLS のバージョン、暗号スイート、証明書方針は Cloudflare 側で、リポジトリに設定が無い。内部は Service Binding と共有秘密。

### V13 Configuration

秘密は Wrangler のシークレットで、既定の内部パスワードは無い。デバッグ用ソースマップのアップロードは id の wrangler で切っている。接続上限と秘密の期限は文書が薄い。

### V14 Data Protection

API の `Cache-Control: no-store`、ブラウザに秘密を置かないこと、RP への最小化は実装がある。データの分類表と保持期限が無い。ログアウトは Cookie 削除で、`Clear-Site-Data` は無い。

### V15 Secure Coding and Architecture

依存の high 以上は CI の `npm audit` が落とす。修正期限と SBOM は無い。質量代入、オープンリダイレクトの追従、IP ヘッダーの扱いはコードで抑えている。

### V16 Security Logging and Error Handling

未処理例外は汎用メッセージと固定ログ。ログインの一部と管理操作は D1 に残る。認可拒否のログ、改ざんできない保管、別系統への通知は足りない。`docs/error-logging-privacy.md` は console の最小化であって台帳ではない。

### V17 WebRTC

WebRTC は無い。章ごと対象外。
