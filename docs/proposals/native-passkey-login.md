# Native passkey HTTP draft, 2026-11-07 UTC

Status: default-off implementation proposal. No deployment configuration or migration is enabled by this increment. Signup and real browser/Workers rollout validation remain separate gates.

## Minimum coherent increment

Expose a **separate discoverable passkey login**, gated by literal `PASSKEY_LOGIN_ENABLED === "true"` at the IdP. The BFF has its own default-off visibility flag. A wrong/missing flag is off; missing origin, long cookie secret, DB, or auth limiter is fail-closed. No flag or binding is added to deployment configuration.

`OAuthProvider`, `ALL_PROVIDERS`, SNS linking, and existing OAuth routes remain separate. `passkey` is only a historical `auth_codes.provider` / `login_events.provider` method label. No invented OAuth provider is configured.

The current user-bound `passkey-flow.authenticationOptions()` includes credential IDs and must not be exposed behind an unauthenticated email lookup. The new discoverable flow issues an account-independent `user_id = NULL` challenge. A posted credential ID is only an untrusted lookup hint. The candidate owner is authenticated only after a real WebAuthn signature, required UP and UV, exact RP/origin, exact non-null stored userHandle, challenge claim, and credential registration-generation/counter CAS all succeed.

## HTTP and UI

- `GET /auth/passkey/start`: independently validates BFF callback or current service/redirect registration, state, S256 PKCE, nonce, scope and current resource. External services always require S256 PKCE. A BFF callback must match a configured BFF origin and `/auth/callback` exactly, without userinfo/query/fragment. Duplicate, unsupported/link/provider parameters and oversized aggregate continuation state are rejected. No challenge, user, email proof or passkey is consumed/created here.
- It sets two Secure/HttpOnly/SameSite=Lax/Path=/ `__Host-` cookies, no Domain, then 303s to `/auth/passkey`, removing authorization parameters from subsequent page URLs. Their AES-256-GCM keys derive from existing `COOKIE_SECRET` using HKDF-SHA256, separate salt/context and purpose. AEAD additional data binds origin+purpose. Expiry is checked server-side, max 600s. Plaintext 2600 bytes / encoded 3600 characters are bounded so a cookie cannot silently overflow.
- The browser cookie holds a fresh random 32-byte value. The continuation holds its SHA256 hash, a separate fresh transaction, CSRF, expiry and validated authorization context. A challenge binds to SHA256-base64url(browser value + transaction). This prevents swapping the target service in the same browser after an assertion was requested. A later login start replaces both cookies, intentionally making older tabs fail closed.
- `GET /auth/passkey`: self-contained IdP-origin HTML, strict nonce CSP, no external assets/CDN, no-store, no-referrer, no framing. It makes no network/WebAuthn request until the sign-in button is clicked. `form-action` includes only self plus the validated callback origin because Chromium checks POST redirect destinations too.
- `POST /auth/passkey/options`: exact raw Origin equality with configured IdP origin, same-origin Fetch Metadata when present, exact CSRF and boolean explicit confirmation, account-independent options. Only `{options}` is returned. No email, owner, challenge ID, browser binding, authority or receipt.
- `POST /auth/passkey/verify`: same Origin/CSRF gate, one bounded URL-encoded form with exactly CSRF+credential. A normal top-level form POST, not fetch, permits the established code redirect to the BFF or registered client. Content length is not trusted: total read bytes are capped at 32 KiB, even for false/missing length, before JSON parsing. Compressed requests are rejected.
- Every request requires the configured auth IP limiter, with a separate native prefix. Missing/throwing limiter is fail-closed. Public failures are generic and no raw exception is logged by these handlers.
- Following verified signature and CAS, the current user is reloaded and ban/email verification/lockout are checked. Current client ID + immutable service ID, current registered callback, current resource ID (also pinned as expectedResourceServerId in the finalizer's own lookup), and the existing finalizer's resource subject rules are rechecked. The existing `finalizeLogin` issues the ordinary 60s single-use authorization code; state, nonce, S256, scope and resource are carried unchanged. Token exchange remains existing code.
- Browser cancellation re-enables the button. Double clicks do not create parallel prompts. Page navigation aborts pending credential work; BFCache restoration reloads instead of reusing a stale flow. Failed/lost completion is never automatically retried. A fresh ceremony is required.

## BFF integration included in the candidate

- Separate `/auth/passkey` BFF entry sets the existing BFF OAuth-state cookie and uses the existing `/auth/callback` code exchange. Query-supplied state, target and provider cannot override this BFF context.
- `/auth/passkey/status` reveals only the explicit BFF visibility flag. The static login page's native link remains hidden unless it returns true; unavailable status remains hidden.
- The external-service `/login` chooser optionally adds a distinct passkey link directly to the IdP with the original client, callback, state, nonce, PKCE, scope and resource. Ordinary provider links are unchanged.
- No admin BFF visibility/link is added in this increment, although the IdP validates a configured admin callback under the same strict rules.

## Expired challenge cleanup

The candidate scheduled path calls a native cleanup helper. With no literal enable flag, it performs no DB query. With the flag enabled, it checks sqlite_master for the proposed challenge table before deleting only expired challenges. An absent schema returns schema_missing and is reported as incomplete; a database exception is not turned into success. Email intent/outbox cleanup is not enabled because no public signup is connected. The repository currently declares a daily 00:00 UTC cron, unchanged by this draft. Deployment must verify the cron actually runs and evaluate daily peak storage capacity before enablement; an unused or missing schedule does not become operational just because a helper is present.

## Deliberately unfinished / pre-enable gates

1. This increment signs in **already enrolled discoverable passkeys**. There is no public signup or email verification handler, no existing-account linking or recovery, and no email-as-login shortcut.
2. Both passkey schema deployment and rollout configuration are outside this task. Runtime DB errors fail closed; absence of migrations is not reported as a functioning feature.
3. Formal Vite+ 1.5 / Node 22 / TS7 CI is not substituted by the cached local Vite+ 0.1.24 / Node 24 / TS6 results. A current CI run on the exact integration bytes is needed.
4. Real browser rendering, CSP on actual cross-origin form redirects, physical authenticator or browser virtual-authenticator flows, BFCache behavior and actual Workers/D1 execution remain pre-enable verification. UI lifecycle tests execute the emitted JavaScript with explicit test doubles, not a browser.
5. Existing token/exchange handlers are unchanged. A proof-time account check is covered; existing code-exchange/refresh semantics after a later account-policy change are not strengthened here. Review the desired passkey-specific verified-email recheck at code exchange before rollout.
6. Existing `finalizeLogin` checks are not a single SQL transaction with auth-code insert. This draft preserves its concurrency semantics rather than claiming an atomic account/resource/code authorization boundary.
7. Cookie aggregate context is intentionally stricter than individual legacy parameter limits. Oversized clients receive a generic error, not truncation.
8. Failed signature input does not increment a claimed owner's account lockout count: unauthenticated credential hints must not become an account-locking DoS primitive. Existing lockouts are enforced after proof and IP limits apply throughout.

## Next signup integration (design only, not mounted)

Use a separate `EMAIL_PASSKEY_SIGNUP_ENABLED === "true"` gate, independently approved delivery binding and fixed sender `noreply@id.0g0.xyz`. The approved paid-plan statement does not provision a binding or authorize new credentials/DNS/contract steps. Fail closed without every required runtime dependency, including dedicated per-IP and aggregate delivery controls. Do not reuse native login purpose/cookie namespaces for enrollment authority.

1. IdP signup page installs a browser-bound flow and CSRF. A user explicitly submits the email and intended signup action. `POST /auth/email/start` caps total input, validates exact origin+CSRF, uses `createEmailSignupIntent`, and returns the same generic accepted presentation regardless of existing account/cap/rejection. Always issue an indistinguishable encrypted continuation (a dummy intent for suppressed requests if needed), avoiding account-existence leaks through cookie length/presence or response shape.
2. Send only through `deliverEmailSignupIntent` and `sendVerificationEmail`. Claim before exactly one provider invocation. Keep accepted/rejected/uncertain delivery details internal. Never resend a claimed/uncertain token. A dropped response does not prove the send failed. Delivery acceptance is not email ownership.
3. Email link stays `https://id.0g0.xyz/auth/email/verify#token=...`. The landing GET must perform no DB verification/write, no token consumption, no registration and no automatic POST. Inline nonce-authorized script must capture the fragment into memory and immediately `history.replaceState(null, '', '/auth/email/verify')` before any network/resource load. No localStorage/sessionStorage, telemetry, third-party assets, or reflected token.
4. Display “メールアドレスを確認して登録を続ける” and require its explicit click. Only that action sends the in-memory token via same-origin bounded POST, with CSRF, same original browser cookie, and server-read intent ID. Opening a link on a different browser fails closed; it must not silently rebind proof to a new device. A duplicate or expired proof is generic failure.
5. `verifyEmailSignupIntent` atomically consumes token+installs the authority hash. Seal the winning raw authority in a separate short-lived AEAD enrollment cookie (purpose and origin bound, with original browser hash/transaction/expiry), never JSON, HTML, URL, logs, plain signed cookies, or readable storage. No authority is returned for a losing race. Lost authority response requires a fresh user-initiated intent; possession of receipt is not authentication.
6. Registration options resolve the verified intent server-side and use `createPasskeyFlow.registrationOptions`; the API returns only browser options. Pending ID and authority remain server/sealed state. Repeated options should resume the same pending ceremony, not replace it. Display name remains bounded and validated; typed email alone can never link an existing OAuth account.
7. Explicit registration completion calls the real verifier and atomic commit helper. Do **not** issue an OAuth code from `created`, an attestation-none registration result, or a reconciliation receipt. Registration is not a signed authentication assertion. On `uncertain`, do not repeat account creation; reconcile read-only internally, then require a fresh authentication ceremony.
8. After successful registration, require a **fresh `get` challenge and new credential signature** through the native login route before ordinary code finalization. No email-only login/recovery is introduced. Ban, lockout, verified email, credential generation, client, callback and resource state remain current checks.

Recommended signup regressions: scanner GET/HEAD has zero side effects; fragment removal precedes any fetch; no automatic POST; explicit confirmation only; cross-browser token rejection; duplicate proof wins once; token not in access-log URL or Referer; authority not in response JSON/HTML; existing user and suppressed delivery shape/cookie indistinguishable; sender uncertain never resends; new credential creation never issues a code; only fresh signed authentication does; cancellation/reload/back-forward/repeated clicks fail safely.
